# ZIME 译文质量审计与优化建议

日期：2026-09-08。状态：只读分析；未修改程序、词库或已安装输入法。

## 结论

当前问题不仅是 CC-CEDICT 含有面向读者的说明，而是 ZIME 的转换链路同时
存在漏过滤、误过滤、引用丢失、读音混排。应先修复数据解释方式，再评估
更大词库；直接扩库或继续追加字符串黑名单不能解决这些问题。

上一次仅清除括号、拼音和少数前缀的实现不够完整。尤其不能简单追加
“删除所有 abbr. / see / also written 开头的字符串”作为通用修复。

## 核验范围与统计口径

审计本地固定源 `data/zime/cedict.txt.gz`、生成脚本、SQLite 索引、当前 Swift
释义投影和候选上屏数据结构，并与 CC-CEDICT 官方格式说明核对。
直接调用生产 `ZIMELocalLexicon` 进行离线诊断，未向真实文档注入按键。

- 原始源词条：124,988；按源分隔符统计的释义片段：199,654。
- 当前索引保留的片段：190,156；7,004 个源记录的 senses 已变为 `[]`。
  这是源记录数，不等于 7,004 个界面候选都无译文：同字形其他记录、原生
  英文词典或已启用的云服务可能另有结果。
- 源中以 `abbr. for` 开头的片段 401 个，涉及 384 个源记录；`abbr. to`
  59 个。它们既有纯说明，也有“引用 + 有效英文释义”的混合格式。
- 49,414 个原始片段包含括号；不能将其都视为无用注释。
- 对现有索引逐条应用当前生产 core 投影后，244 个原本非空的源记录变为空；
  包括只有发音说明的记录，也包括本应保留的语法/功能释义，不能将 244
  全部计为可恢复翻译。
- 投影后仍含 `|` 的片段有 4,751 个。这是待审查风险集合，并非自动认定
  全部错误，正文中的字形举例等也可能需要保留。
- 6,240 个源记录在当前去重投影后仍有超过 3 个候选释义；实际可选译文
  在多个层次被固定截成前 3 项。
- 对空记录做保守的“完整引用 + 精确读音”路径探测：6,871 条一跳能到达
  非空记录，另 31 条需二跳。这只是可达性，不是已验证恢复数量；正式实现
  还必须校验精确繁简词头、关系类型、歧义与循环。

## 已复现的典型问题

以下“当前结果”来自本地生产释义组件，不代表复现了用户所有应用中的候选排序。

| 词条 | 当前结果/问题 | 应优化为 |
| --- | --- | --- |
| 费城 | 正确城市名后又出现 `abbr. for 費拉德爾菲亞\|费拉德尔菲亚` | 保留 `Philadelphia, Pennsylvania`；简称关系仅为可选详情 |
| 世博 | `abbr. for 世界博覽會\|世界博览会, World Expo` | 提取/解析到 `World Expo`，不删除整条有效释义 |
| 上汽 | 引用说明与 `Shanghai Automotive Industry Corp.` 混在一行 | 保留公司英文名称；简称关系单独保存 |
| 下次见、看穿、亦作 | 索引中变为空释义 | 恢复 `see you next time`、`see through`、`also written as` 等正常正文 |
| 明天见 | `see you tomorrow` 被删除，只剩食物消化相关的冷门俚语 | 恢复日常意思并优先展示；俚语保留为次要含义 |
| 瞭解 | 引用被删除，直接查这个字形无释义 | 沿明确的 variant 引用找到“了解”的对应读音释义 |
| 之 | 当前只剩 `him / her / it`，所有格功能释义丢失 | 保留核心语法含义，避免把完整功能说明当作可删注释 |
| 行 | 当前前项是 `used in 道行`，hang/heng/xing 不同读音的释义混排 | 解析关系并根据实际可获得的候选读音筛选/排序，不能让引用说明抢占译义位置 |

“一分熟”的 `rare (of steak)` 投影成 `rare` 说明另一种边界：去掉的文字
虽然不该随翻译上屏，却含有辨义信息。需要保留为元数据，而不是不可逆删除。

## 根因

1. **建库阶段提前删内容。** `scripts/build-zime-lexicon:24` 使用字符串
   前缀直接 reject。正常英语 `see you tomorrow` 和真正的 `see 某词[拼音]`
   被同等对待；被删内容在运行时无法找回。源文件仍在，重建可以恢复。
2. **显示层没有语义分类。** `sources/ZIMELocalLexicon.swift:169` 主要处理
   括号和少数前缀，既漏掉 `abbr.`、`erhua variant` 等格式，也会吞掉括号内
   的完整释义；仅删除拼音会留下中文引用和 `|`。
3. **未实现引用解析。** 原始数据中大量异体、同义和缩写关系本来能提供词义，
   但当前数据库只剩被筛过的字符串，没有可追踪的引用边。
4. **读音和释义排序不足。** 原始词条存有拼音，查询/投影却主要按候选文字
   合并，当前 priority 只粗略区分专名与 bound form；不能视作词义频率。
5. **过早、重复截断。** 本地注释、结构化传输、解析和译文菜单都有前三项
   限制。菜单 Row ID 还依赖每个源词最多三项的假设，不能只删除 prefix(3)。
6. **现有测试验证了错误规则的一致性。** `tests/verify_zime_lexicon.rb:49`
   也重复相同删除规则，所以源记录数量、拼音和可重建性通过，并不代表
   原始释义无损或语义正确。上次新增的 `see you` 单元测试没有覆盖建库阶段。

## 推荐的数据处理方式

### 1. 原始数据无损，解析结果单独存储

保留原始繁体、简体、读音、全部原文片段和来源版本。新增明确的类型与来源：
普通译义、同义表达、语法释义、地区/语域标签、引用关系、例句、发音说明。
所有简化结果都能追溯到源记录和原始片段。

发布版数据库在构建时生成解析结果和可继承的译义；输入时只查索引、按地区
和可用读音排序，再使用有界缓存。不要在每个按键上递归全库或调用模型。
数据库架构版本应独立迁移；当前 SQLite user_version=2 不等于 CC-CEDICT V2。
当前固定源是单括号拼音的 V1 格式导出，不能直接换下载格式而不更新解析器。

### 2. 引用必须按关系类型处理

- 明确的 `variant of`、`see` 等等价关系：按引用中的繁简词头与读音解析，
  继承对应译义，记录来源。字形不改写、不通过全局简化粗暴合并。
- `abbr. for/of`：已有正常译义时只记录简称关系；混合行应提取其中的正文。
  仅有引用时才尝试解析全称，不假定引用目标一定存在。
- `abbr. to`：反向简称说明，不应把其再次当成需要跟随的等价边，以免形成
  费城/全称、世博/全称之间的循环或重复。
- `see also`、`cf.`、不明确的旧格式：不是可靠的等价声明，不能盲目继承。
- `used in`：词中用字说明，不代表单字等于整个词的意思。作为详情关联，
  不拿词语的翻译冒充该字的独立英文意思。
- 对所有解析实施 visited 集合、明确深度上限、目标歧义检测、失效目标报告。
  单字、扩展区汉字、非汉字词头以及读音中的大小写区别都需要单独测试。

这些区分符合官方对引用替换、非等价关联与构词用字的说明，而不是按字符串
是否“看起来像英文”猜测。[引用规范](https://cc-cedict.org/wiki/references)、
[开发者建议](https://cc-cedict.org/wiki/developers)、
[构词用字说明](https://cc-cedict.org/wiki/bound_forms)。

### 3. 精简文字，不销毁含义

- 长例句、词源、发音、简称解释不进入可上屏译文。
- 核心释义继续共享给候选显示和数字选词；不同义项保留 `/` 分隔，不用长度
  截断代替语义清理。同一义项内的同义词分组也要保留。
- 括号中的语法释义不能一律删；辨义范围保留在结构化元数据中。对难以自动
  拆分的功能词使用经复核的短释义，不臆造一个英文单词作为通用等价翻译。
- “翻译显示完整注释”仍默认关闭，只控制悬停/辅助功能详情，绝不改变上屏。
- 去重优先按解析后的义项与规范化文本，不用模糊相似度合并不同含义。
- CC-CEDICT、原生英文词典、云 API 分别适配各自格式，共用最终数据结构；
  不应对云端自然语言译文也无条件套用 CC-CEDICT 的括号/引用清洗规则。

官方区分 `/` 与 `;`，也指出括号可能用于辨义；这些信息应解析后再选择是否
展示，而非直接丢弃。[格式说明](https://cc-cedict.org/wiki/syntax_v2#definition)。

### 4. 排序与覆盖率

优先完整的常用直接译义，次选可靠继承的译义；地区作为偏好，不恢复“地区
限制”导致的无译文。不能把所有口语、专业或 bound form 一律降级，因为它们
有时就是该词的主要意思。可维护小规模、有来源的义项排序修订表，处理规则
无法可靠判断的高频词；不能将修订表变成替代通用解析的大量特判。

候选若能提供准确读音，使用它约束多音字；只有模糊/缩写输入时不能假装已知
读音，要验证 Rime 到 Host 的数据边界。此项建议在前述词库修复稳定后实施。

释义数据不要在传输途中重复截断。是否扩展可选义项上限应作为单独 UI 改动：
保留现有 3–9 行每页，用稳定的“源候选身份 + 义项身份”支撑分页和异步刷新，
避免改动导致学习归属错位。本轮首先保证现有槽位都是真正且排序合理的译义。

## 分阶段实施建议

**P0：停止丢失正常译义。** 无损保存原文、识别真正引用语法、修复日常词
误删，建立覆盖建库到上屏全过程的回归样例。现有旧索引必须重建，仅更新
Swift 无法找回已删除的内容。

**P1：结构化解析和受控引用继承。** 解决费城/世博类混合说明、繁体引用缺义、
功能词括号误删；清理不再需要的显示层补丁。生成每类未解析/歧义/循环报告，
先审查高频候选，不静默输出未经验证的“核心译义”。

**P2：读音、义项排序和剩余覆盖率。** 再核查常用候选缺义率、长释义比例、
多音字与义项分页。只有在这些指标说明现有库确实缺内容时，才比较补充词库，
并保留来源、许可证及优先级；不把接入更多数据当作解析错误的解决办法。

不建议以每词联网或大模型批量自由改写作为第一步。当前确定的问题有本地、
可重建的解决方向；离线优先和云翻译的显式启用边界保持不变。

## 验收要求

1. 固定原始 gzip → 新索引 → 实际注释 → 原文/译文切换 → 数字上屏端到端
   测试，覆盖上表；不是仅测试字符串函数。
2. 必须保住 `see you tomorrow`、`see you next time`、`see through`、
   `also written as`、`also known as` 等真正正文。
3. 对纯引用、正文夹引用、无读音引用、儿化、循环、缺失目标、歧义目标、
   繁简一对多与大小写读音建立独立期望结果，不复制实现规则充当断言。
4. 每条被删除或继承的内容有原因与来源；真正译义丢失、已知引用标记泄漏、
   常用词空译文等作为发布阻断项。统计风险集合需人工/分类复核，不能用
   “任何英文译文包含汉字就失败”这种新的一刀切规则。
5. 保持数字选词、Return 原文、Tab 切换、候选学习归属、3–9 行配置不回退；
   详情开关不改变译文提交结果、不触发额外 API/钥匙串访问。
6. 分别衡量冷查询与缓存命中 p50/p95、9 候选查询耗时、内存和索引体积；
   全库离线审计耗时不能冒充真实输入延迟。该次纯 core 扫描约 0.86 秒只是
   诊断执行时间，没有修改或性能验证新方案。

## 不能承诺的边界

可以消除“已有译义被误删、已有引用不解析、繁简字形被错误屏蔽”这些人为
缺口，但不能保证任意组句、新词和无独立意义的单字都有准确独立英文译词。
确实无可用译义时继续统一显示“无译文”，不拿拼音、引用说明或错误的整词
译义凑数；完整说明仍受用户的详情开关控制。
